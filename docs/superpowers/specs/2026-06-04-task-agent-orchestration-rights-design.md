# ТЗ: задачи как центр управления агентами и правами

Дата: 2026-06-04

## Цель

Сделать проектный менеджер центром управления агентской работой. Задача должна
быть не просто карточкой в kanban, а управляемым рабочим объектом: из нее можно
запустить новую агентскую сессию, подключить существующую сессию workspace,
передать агенту контекст задачи, разрешить агенту писать прогресс, двигать
статусы и обновлять чеклист в пределах прав пользователя.

Мессенджер должен уметь жить отдельно. В будущем обычные пользователи могут
видеть только мессенджер, а проекты, задачи, workspaces и AI будут скрыты и
запрещены сервером.

## Базовые понятия

- `Задача` - цель, описание, статус, чеклист, комментарии, вложения, критерии
  готовности и агентские события.
- `Проект` - контейнер задач, участников, проектных групп, чатов и связанных
  рабочих пространств.
- `Workspace` / `Рабочее пространство` - локальная папка/среда CodeWhale, где
  запускаются агентские сценарии.
- `Агентская сессия` - конкретный запуск агента в workspace, который может быть
  связан с одной или несколькими задачами, но основной сценарий - запуск из
  одной задачи.
- `Agent Run Policy` - вычисленная сервером политика запуска: режим, разрешенные
  плагины, запреты, права на запись в задачу и workspace.

## Суперадмин

Никита с телефоном `+79679812438` / `79679812438` является `superadmin`.

Только `superadmin` может:

- выдавать и отзывать доступ к workspace;
- назначать роли уровня приложения;
- видеть аудит действий;
- разрешать рискованные агентские режимы;
- запускать агентские сессии с повышенным набором плагинов.

## Роли

- `superadmin` - полный доступ, выдача workspace-доступов и аудит.
- `messenger_user` - только мессенджер, контакты, личные и групповые чаты.
- `project_member` - просмотр доступных проектов и задач, комментарии.
- `project_admin` - управление конкретным проектом, задачами и группами проекта.
- `workspace_user` - просмотр и использование выданных workspace.
- `agent_operator` - запуск и подключение агентов к задачам.
- `blocked` - отключенный пользователь.

Роли не должны быть единственным источником прав. Сервер должен отдавать
конкретные capabilities.

## Режимы агента

1. `План`
   - читает задачу и проектный контекст;
   - пишет план/вопросы;
   - не меняет файлы и статус задачи.

2. `Чат`
   - отвечает в агентском чате по задаче;
   - не меняет задачу.

3. `Комментатор`
   - пишет комментарии в задачу;
   - может добавлять итоговые заметки;
   - не меняет статус.

4. `Исполнитель`
   - читает задачу и workspace;
   - может менять файлы workspace;
   - пишет комментарии;
   - обновляет чеклист;
   - переводит задачу в `В работе` и `На проверке`.

5. `Ревьюер`
   - проверяет результат другой сессии;
   - пишет замечания;
   - может вернуть задачу в `В работе` или предложить `Готово`.

6. `Автопилот`
   - может создавать подзадачи;
   - может запускать дополнительные сессии;
   - может вести задачу до `На проверке`;
   - финальное закрытие остается за человеком, если отдельно не разрешено.

7. `YOLO`
   - максимально автономный режим;
   - доступен только `superadmin`;
   - по умолчанию выключен.

## Плагины и инструменты

Плагины должны выдаваться по политике запуска, а не выбираться агентом
самостоятельно.

Категории:

- `task_context` - читать задачу, комментарии, чеклист.
- `task_write` - писать комментарии, менять статус, чеклист.
- `workspace_read` - читать файлы workspace.
- `workspace_write` - менять файлы workspace.
- `git` - branch/commit/push.
- `github` - PR, issues, CI logs.
- `browser` - UI-проверки и screenshots.
- `deploy` - деплой и серверные команды.
- `admin` - роли, доступы, аудит; агентам запрещен, кроме явного
  superadmin-сценария без автозапуска.

## Типы задач и политика по умолчанию

- `research` - `План`, `Чат`, без записи файлов.
- `feature` - `План`, `Исполнитель`, `Ревьюер`, workspace write при наличии
  прав.
- `bugfix` - `Исполнитель`, tests, git при наличии прав.
- `ui` - `browser`, screenshots, workspace write при наличии прав.
- `security` - только `План`/`Ревьюер`, без автопилота, усиленный аудит.
- `deploy` - только `superadmin` или отдельный `agent.deploy`.
- `refactor` - без `YOLO`, обязательно reviewer.

## Связь задачи и агентской сессии

У задачи может быть несколько связанных агентских сессий:

- активная сессия;
- старые завершенные сессии;
- reviewer-сессия;
- исследовательская сессия;
- сессия фикса багов.

В задаче нужна вкладка `Агент`:

- подключить существующую сессию;
- запустить нового агента;
- выбрать режим;
- увидеть разрешенные плагины;
- отправить агенту контекст задачи;
- остановить;
- перезапустить;
- запросить отчет;
- отправить на ревью;
- отключить от задачи.

## Context Pack задачи

При запуске агент получает:

- название задачи;
- описание;
- проект;
- workspace;
- статус;
- приоритет;
- ответственных;
- дедлайн;
- чеклист;
- комментарии;
- вложения/файлы;
- критерии готовности;
- последние сообщения проектного чата;
- предыдущие агентские итоги по этой задаче;
- effective policy.

## Что агент может писать обратно

Агентские события:

- `agent_started`
- `agent_connected`
- `agent_comment_added`
- `agent_task_status_changed`
- `agent_checklist_updated`
- `agent_question_added`
- `agent_blocked`
- `agent_summary_added`
- `agent_finished`
- `agent_permission_denied`

Пользовательские тексты должны быть на русском.

## Автоматическое движение задачи

- запуск агента в режиме `Исполнитель` переводит задачу в `В работе`;
- завершение черновика переводит в `На проверке`;
- блокер оставляет `В работе`, но помечает `agent_status = blocked`;
- reviewer может вернуть в `В работе` или предложить `Готово`;
- финальное `Готово` подтверждает человек или `superadmin`.

## Защита tunnel и bridge

Workspace-команды должны идти только с signed ticket, выданным backend.

Ticket содержит:

- `actor_profile`;
- `task_id`;
- `workspace_id`;
- `session_id`;
- `mode`;
- `allowed_plugins`;
- `allowed_commands`;
- `expires_at`;
- подпись backend.

`tunnel_server.py` и `codewhale_bridge.py` отклоняют запуск и команды без
валидного ticket. Старый клиентский `canUseProjectChats(phone)` может остаться
только как UI fallback, но не как защита.

## UI

Для обычного `messenger_user`:

- виден только мессенджер;
- кнопки проектов, задач, workspaces и AI скрыты.

Для пользователя с workspace-доступом:

- видны проекты, задачи и рабочие пространства;
- в задаче доступна вкладка `Агент`;
- доступны только разрешенные режимы и плагины.

Для `superadmin`:

- видна админка пользователей и доступов;
- доступен аудит;
- доступно управление workspace-доступами.

## Аудит

Писать audit/event для:

- выдачи доступа;
- отзыва доступа;
- запуска агентской сессии;
- подключения существующей сессии;
- остановки/kill агента;
- изменения статуса задачи агентом;
- изменения чеклиста агентом;
- отказа по правам;
- изменения ролей.

## Минимальные данные

- `user_roles`
- `role_capabilities`
- `workspace_access`
- `agent_mode_catalog`
- `agent_plugin_catalog`
- `task_agent_sessions`
- `task_agent_events`
- `agent_policy_tickets`
- `audit_logs`

## Критерии приемки

- Никита по телефону `79679812438` получает `superadmin`.
- Обычный пользователь без workspace-доступа видит только мессенджер.
- Пользователь без `tasks.manage_agent` не может запускать агента из задачи.
- Пользователь без `workspaces.use` не может открыть workspace через прямую
  команду.
- Из задачи можно создать новую агентскую сессию.
- Из задачи можно подключить существующую агентскую сессию.
- При запуске агент получает context pack задачи.
- Агентские комментарии появляются в задаче.
- Агент может менять статус только если policy разрешает.
- Агент может обновлять чеклист только если policy разрешает.
- Backend возвращает effective policy для задачи.
- Tunnel/bridge отклоняют команды без policy ticket.
- Все новые UI-подписи и ошибки на русском.
